## 1. 现状与问题

### 1.1 当前数据分布

| 数据 | App 本地 (AsyncStorage) | Server (SQLite) | 备注 |
|---|---|---|---|
| 用户账号 | — | ✅ `users` | phone/role/created_at |
| 运动记录 | ✅ `userData/{owner}/exerciseSessions` | ❌ | mode/emotion/rpe/journal/exercises/types |
| 目标设置 | ✅ `userData/{owner}/goalSettings` | ❌ | targets + smartGoals |
| 用量统计 | ✅ `userData/{owner}/usageStats` | ❌ | usageDays/loginEvents/audioPlays/... |
| 学习进度 | ✅ `userData/{owner}/learningProgress` | ❌ | equipmentId → read/watched/listened |
| 器材收藏 | ✅ `userData/{owner}/bookmarkedItems` | ❌ | — |
| 研究事件 | — | ✅ `research_events` | 事件流（≤16KB metadata） |
| 聊天 | — | ✅ `messages`/`conversations` | — |
| 知情同意 | — | ✅ `research_consents` | — |

**核心障碍**：业务数据全部 `syncStatus: "local-only"`、`remoteId: null`（见 `utils/userStorage.js` 注释 "Placeholder for future cloud sync"），从未上传。

### 1.2 用户身份对应关系

- App 本地 `ownerKey` 形如 `phone:91234567` / `email:...` / `guest` / `name:...`
- Server `users.id` 为 UUID，`phone` 为 `+852XXXXXXXX`
- **同步桥接键**：`phone`（登录/注册用户）——注册/登录成功后必须调用 `ensureUserFolder(user)` 使本地 ownerKey 与账号绑定

## 2. 设计原则

1. **以 App 本地数据为源（source of truth）**：App 仍离线可用，Server 为同步副本（分析用途）
2. **增量同步 + 幂等**：每次写操作生成 `updatedAt`，按 `updatedAt > lastSyncAt` 增量上传；服务端按 `(user_id, local_id)` 唯一键 upsert
3. **离线优先**：无网时写入本地队列，联网后批量补传
4. **与研究事件共存**：`research_events` 继续记录行为事件流（轻量），新表记录**结构化业务数据**（重量）
5. **字段配置化预留**：所有新表带 `metadata_json` 扩展槽，满足 PRD "新字段无需改代码"

## 3. 数据模型设计（server 新增表）

### 3.1 exercise_sessions（运动记录，对应 4.4 训练记录域）

```sql
CREATE TABLE IF NOT EXISTS exercise_sessions (
  id            TEXT PRIMARY KEY,              -- server uuid
  user_id       TEXT NOT NULL,
  local_id      TEXT NOT NULL,                 -- App 端 session.id
  session_date  TEXT NOT NULL,                 -- ISO 完成时间
  duration_sec  INTEGER NOT NULL DEFAULT 0,
  mode          TEXT NOT NULL CHECK (mode IN ('outdoor','home')),
  emotion       INTEGER,                       -- 1-5
  rpe           INTEGER,                       -- 0-10
  journal       TEXT,
  types_json    TEXT NOT NULL DEFAULT '{}',    -- {aerobic,balance,muscle}
  exercises_json TEXT NOT NULL DEFAULT '[]',   -- [{name,reps}]
  metadata_json TEXT NOT NULL DEFAULT '{}',
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  deleted_at    TEXT,
  UNIQUE (user_id, local_id),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS exercise_sessions_user_time
  ON exercise_sessions(user_id, session_date DESC);
```

### 3.2 goal_settings（目标与进度，对应 4.5）

```sql
CREATE TABLE IF NOT EXISTS goal_settings (
  user_id       TEXT PRIMARY KEY,
  targets_json  TEXT NOT NULL DEFAULT '{}',    -- {aerobic:5,balance:3,muscle:2}
  smart_goals_json TEXT NOT NULL DEFAULT '[]', -- [{id,text,weekKey,done}]
  metadata_json TEXT NOT NULL DEFAULT '{}',
  updated_at    TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

### 3.3 usage_stats（用量统计，支撑活跃度/4.2 行为状态）

```sql
CREATE TABLE IF NOT EXISTS usage_stats (
  user_id       TEXT PRIMARY KEY,
  usage_days_json  TEXT NOT NULL DEFAULT '[]', -- ["YYYY-MM-DD"]
  login_events  INTEGER NOT NULL DEFAULT 0,
  intro_loads   INTEGER NOT NULL DEFAULT 0,
  audio_plays   INTEGER NOT NULL DEFAULT 0,
  goals_achieved INTEGER NOT NULL DEFAULT 0,
  outdoor_sessions INTEGER NOT NULL DEFAULT 0,
  home_sessions INTEGER NOT NULL DEFAULT 0,
  tts_plays     INTEGER NOT NULL DEFAULT 0,
  metadata_json TEXT NOT NULL DEFAULT '{}',
  updated_at    TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

### 3.4 learning_progress（学习进度，支撑内容分析）

```sql
CREATE TABLE IF NOT EXISTS learning_progress (
  user_id       TEXT NOT NULL,
  equipment_id  TEXT NOT NULL,
  read_flag     INTEGER NOT NULL DEFAULT 0,
  watched_flag  INTEGER NOT NULL DEFAULT 0,
  listened_flag INTEGER NOT NULL DEFAULT 0,
  updated_at    TEXT NOT NULL,
  PRIMARY KEY (user_id, equipment_id),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

### 3.5 bookmarked_items（收藏，支撑器材偏好分析）

```sql
CREATE TABLE IF NOT EXISTS bookmarked_items (
  user_id       TEXT NOT NULL,
  equipment_id  TEXT NOT NULL,
  created_at    TEXT NOT NULL,
  PRIMARY KEY (user_id, equipment_id),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

### 3.6 sync_state（同步游标，服务端记录每用户最后同步时间）

```sql
CREATE TABLE IF NOT EXISTS sync_state (
  user_id       TEXT PRIMARY KEY,
  last_synced_at TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

## 4. API 设计

### 4.1 统一批量同步端点（推荐：一个端点收全部，减少请求数）

```
POST /api/sync
Authorization: Bearer <token>
Content-Type: application/json

{
  "sessions": [ {localId, date, durationSec, mode, emotion, rpe, journal, types, exercises, updatedAt, deleted} ],
  "goals": { targets, smartGoals, updatedAt },
  "usage": { usageDays, loginEvents, introLoads, audioPlays, goalsAchieved, outdoorSessions, homeSessions, ttsPlays, updatedAt },
  "learning": [ {equipmentId, read, watched, listened, updatedAt} ],
  "bookmarks": [ {equipmentId, createdAt} ],
  "clientTime": "ISO"
}

→ 200 { ok: true, syncedAt: "ISO" }
```

**服务端逻辑**：
1. 鉴权（复用 `authenticatedUser`）
2. 按 `user_id + local_id` upsert sessions（`ON CONFLICT(user_id, local_id) DO UPDATE`）
3. goals/usage 整表替换（小数据，直接 upsert 整体）
4. learning/bookmarks 按主键 upsert/delete
5. 更新 `sync_state.last_synced_at`
6. 响应 `syncedAt` 供 App 推进本地游标

**幂等性**：sessions 以 `updatedAt` 为准 —— 服务端 `updated_at <= 请求 updated_at` 才覆盖，避免乱序覆盖。

### 4.2 可选拆分端点（若需精细控制）

```
POST /api/sync/sessions      — 批量 upsert 运动记录
POST /api/sync/goals         — 上报目标
POST /api/sync/usage         — 上报用量
POST /api/sync/learning      — 上报学习进度
POST /api/sync/bookmarks     — 上报收藏
```

> 团队建议：先做 4.1 单端点（实现简单、请求少、利于后续加字段），拆分端点留作演进。

### 4.3 校验与限制

- 单次请求体 ≤ 1 MB（超限分页上传，客户端按 500 条/批切片）
- `session_date`/`updatedAt` 必须是 ISO 8601
- `mode`/`emotion(1-5)`/`rpe(0-10)` 范围校验，非法值整批拒绝返回 `400 invalidPayload`
- 无 token → 401；guest 用户（无账号）→ 跳过同步（本地保留）

## 5. App 端同步实现方案

### 5.1 新增 `utils/sync.js`

```js
// 同步游标（本地）
const SYNC_CURSOR_KEY = "syncCursor";   // { lastSyncedAt: "ISO" }

export async function syncNow(token) {
  const [sessions, goals, usage, learning, bookmarks] = await Promise.all([
    getSessions(), getGoalState(), getUsageStats(),
    getLearningProgress(), getBookmarks(),
  ]);
  // 增量：只取 updatedAt > lastSyncedAt 的 sessions（本地 session 已有 date 字段，
  // 增补 updatedAt 于 saveSession 时写入）
  const payload = buildSyncPayload({ sessions, goals, usage, learning, bookmarks });
  const res = await fetch(`${API_BASE_URL}/sync`, {
    method: "POST",
    headers: { "Content-Type": "application/json", Authorization: `Bearer ${token}` },
    body: JSON.stringify(payload),
  });
  if (res.ok) {
    await AsyncStorage.setItem(SYNC_CURSOR_KEY, JSON.stringify({ lastSyncedAt: res.syncedAt }));
  }
}
```

### 5.2 写入即标记（改造现有 utils）

| 文件 | 改动 |
|---|---|
| `utils/sessions.js` | `saveSession` 时给 session 附加 `updatedAt = new Date().toISOString()`；`deleteSession` 保留 tombstone（deleted 标记） |
| `utils/goals.js` | `saveGoalState` 附加 `updatedAt` |
| `utils/usage.js` | `saveStats` 附加 `updatedAt` |
| `utils/learning.js` | `markLearning` 附加 `updatedAt` |
| `utils/bookmarks.js` | `saveBookmarks` 附加 `updatedAt` |

### 5.3 同步触发时机

1. **登录成功后**：`AuthContext` 登录成功 → 后台静默同步
2. **保存运动记录后**：`session/summary.js` `handleSave` 后延迟 3s 同步
3. **App 进入前台**（AppState active）→ 若 `lastSyncedAt` 超 5 分钟 → 同步
4. **手动刷新**：设置页加「立即同步」按钮（调试用）
5. **失败重试**：失败时标记 `pendingSync = true`，下次触发时重试；不做复杂队列（MVP）

### 5.4 guest 用户处理

- guest 无 server 账号 → 跳过同步（`syncNow` 开头判断 `!user || user.isGuest` 直接 return）
- 登录后 `ensureUserFolder(user)` 已绑定 ownerKey → 数据归属正确

## 7. 安全与合规（科研场景强制项）

1. **数据最小化**：上传内容仅限上述结构化字段，`journal`/`smartGoals.text` 为用户自由文本，需在 PRD 中明确其分析用途并取得知情同意覆盖
2. **研究同意绑定**：同步端点检查 `research_consents` 最新状态；`withdrawn` 用户拒绝写入（`403 consentWithdrawn`）
3. **审计**：同步写入 `system_logs`（action=`sync.upload`，target_type=user，target_id=user_id，metadata=批次大小/耗时）
4. **脱敏**：分析/导出时 `phone` 默认打码（`+852****5678`），姓名仅管理员可见（对应 PRD 非功能「敏感字段脱敏」）

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 老用户本地数据无 updatedAt | 增量同步漏传 | 首次同步全量上传（`lastSyncedAt` 为空时不过滤） |
| AsyncStorage 大数据量 | 性能/超限 | sessions 分批上传（≤500 条/批） |
| guest 数据无法归属 | 研究样本缺失 | 注册引导 + 登录后合并（后续迭代） |
| 时间戳乱序 | 数据覆盖错乱 | 服务端按 updatedAt 比较后再 upsert |
| 知情同意撤回后旧数据 | 合规风险 | withdrawn 后禁止新写入 + 导出时排除（或按 IRB 要求销毁） |
